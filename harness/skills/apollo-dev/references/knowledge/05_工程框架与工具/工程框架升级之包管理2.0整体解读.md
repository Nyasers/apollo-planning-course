比如例子中的配置，我们将apollo版本限定为9.0.0-beta-r0，这样我们在cyberfile.xml中声明的依赖包都将会使用这个版本

###### 如何替换我们自己的检测算法

首先我们可以修改cyberfile.xml，选择感知lidar相关的其它功能包

```xml
  <!-- 删除lidar检测包
  <depend repo_name="perception-lidar-detection" type="binary">perception-lidar-detection</depend>
  -->
  <depend repo_name="perception-lidar-detection-filter" type="binary">perception-lidar-detection-filter</depend>
  <depend repo_name="perception-launch" type="binary">perception-launch</depend>
  <depend repo_name="perception-lidar-tracking" type="binary">perception-lidar-tracking</depend>
  <depend repo_name="perception-msg-adapter" type="binary">perception-msg-adapter</depend>
  <depend repo_name="perception-pointcloud-ground-detection" type="binary">perception-pointcloud-ground-detection</depend>
  <depend repo_name="perception-pointcloud-map-based-roi" type="binary">perception-pointcloud-map-based-roi</depend>
  <depend repo_name="perception-pointcloud-preprocess" type="binary">perception-pointcloud-preprocess</depend>
```
然后再新增一个自己的lidar检测组件包

```bash
buildtool create --template component modules/perception/my_lidar_detection
```
开发完成后再编译

```bash
buildtool build --gpu
```
最后再修改launch启动文件（

```bash
modules/perception/launch/perception_lidar.launch），将lidar_detection替换成新增加的my_lidar_detection
```

```xml
<cyber>
  <desc>Apollo lidar 3d object detection</desc>
  <version>1.0.0</version>
  <module>
    <name>lidar</name>
    <dag_conf>/apollo/modules/perception/msg_adapter/dag/msg_adapter.dag</dag_conf>
    <dag_conf>/apollo/modules/perception/pointcloud_preprocess/dag/pointcloud_preprocess.dag</dag_conf>
    <dag_conf>/apollo/modules/perception/pointcloud_map_based_roi/dag/pointcloud_map_based_roi.dag</dag_conf>
    <dag_conf>/apollo/modules/perception/pointcloud_ground_detection/dag/pointcloud_ground_detection.dag</dag_conf>
    <dag_conf>/apollo/modules/perception/my_lidar_detection/dag/my_lidar_detection.dag</dag_conf>
    <dag_conf>/apollo/modules/perception/lidar_detection_filter/dag/lidar_detection_filter.dag</dag_conf>
    <dag_conf>/apollo/modules/perception/lidar_tracking/dag/lidar_tracking.dag</dag_conf>
    <process_name>lidar</process_name>
    <version>1.0.0</version>
  </module>
</cyber>
```

### 包

刚才我们提到了包和组件的概念，

#### 包

> 按照一定粒度进行规范化组织和管理的功能代码及其相关的数据配置文件和编译产出，一方面支持直接使用产出包的方式直接使用组件，另一方面规范组件的依赖关系以及组件的粒度，从而降低组件的使用/复用难度，提升研发效率
> 在 Apollo 软件包管理模式中，一个包的源码包括以下内容：
> cyberfile.xml(必须): 包的描述文件，描述了该包的名称、所在工作空间路径、依赖等信息
> BUILD（必须）: 即 bazel 的 BUILD 文件，描述了模块中 c++ 源码， python 源码，配置文件，数据文件等该组织成什么形式进行编译
> 一系列的源码，数据文件，配置文件等（可选）

在这里，core包作为示例中的依赖声明，仅包含了cyberfile.xml和BUILD两个文件

###### cyberfile.xml

cyberfile.xml 在包所在目录下（也就是说一个包含cyberfile.xml文件的目录会被视作一个包）。同时该目录也是该包的源码路径，其子目录内不允许再有其它 cyberfile.xml 文件（即不支持嵌套）。

> 其中，一些比较重要的属性：
> name: 模块的名称。
> version: 模块版本号，对于本地的源码，其值填local即可。
> type: 模块的类型，必须为module。
> src_path: 模块在工作空间下源码的路径。

> builder: 底层编译工具，当前仅支持 bazel。

###### BUILD

BUILD 文件即 bazel 的 BUILD 文件，它告诉 Bazel 如何编译所需的输出，例如可执行的二进制文件或库。

在软件包管理模式中，新版Apollo 在 bazel 的基础上，提供了一些宏，规则，例如 core 的 BUILD 文件

```python
load("//tools:apollo_package.bzl", "apollo_package")

package(default_visibility = ["//visibility:public"])

apollo_package()
```
其中apollo_package是软件包管理模式新增的宏，在包管理模式下，所有模块源码的BUILD文件中都需要添加该宏，保证模块源码可以正常的编译，部署，同时也让包的写法更加简单。

除此之外，Apollo为c++源码、python源码、proto源码提供了相应的规则，例如在cyber源码的 BUILD 文件中：

```python
load("//tools:apollo_package.bzl", "apollo_cc_library", "apollo_package")

apollo_cc_library(
    name = "cyber_state",
    srcs = ["state.cc",],
    hdrs = ["state.h",],
    deps = ["//cyber/common:cyber_common",],
)

apollo_package()
```
在软件包管理模式下，请使用 Apollo 提供的规则，这些规则分别有：

apollo_cc_library：声明该 target 生成动态库，替代 bazel 原生 cc_library
apollo_cc_binary：声明该 target 生成可执行文件，替代 bazel 原生 cc_binary
apollo_cc_test：声明该 target 生成测试文件，替代 bazel 原生 cc_test
apollo_component：声明该 target 生成一个 Apollo 组件
apollo_plugin：声明该 target 生成一个 Apollo 插件
apollo_cc_library, apollo_cc_binary, apollo_cc_test规则的使用方式与 bazel 原生规则一致。

apollo_component, apollo_plugin 这两个规则让我们可以更方便地声明组件和插件的编译方式。

##### 组件

#### 组件

在自动驾驶系统中，模块（如感知、定位、控制系统......）以Cyber RT下的一个或多个组件的形式存在。每个组件通过Cyber Channel与其他组件通信。组件概念不仅将模块解耦，还提供了将模块划分为组件的灵活性。

在新版本中，我们可以通过buildtool工具快速创建一个组件包

```bash
buildtool create --template component sample_component
```
> ‍–template 参数声明了创建的模版是 component，sample_component 声明了该 component 的源码路径

执行完毕后，工作空间下会多出了 sample_component 目录：

```

|-- BUILD
|-- conf
|   |-- sample_component.conf
|   `-- sample_component.pb.txt
|-- cyberfile.xml
|-- dag
|   `-- sample_component.dag
|-- launch
```

其中：

BUILD：告诉 bazel 如何编译这个组件
conf：保存该 component 的配置文件，其中 sample_component.pb.txt 的内容会被解析成 sample_component.proto 定义的 SampleComponentConfig 类型；sample_component.conf 声明了一些 gflags
dag, launch：保存该组件的启动文件
proto：保存该组件配置，消息的proto message定义
c++源码：描述该组件的初始化以及接收到相应消息的行为
该示例 component 会监听 /apollo/sample_component channel，接收到消息后在终端打出相应消息。

由于该示例是一个 component，因此在 BUILD 文件中使用了apollo_component规则：

```python
apollo_component(
    name = "libsample_component_component.so",
    srcs = [
        "sample_component.cc",
    ],
    hdrs = [
        "sample_component.h",
    ],
    deps = [
        "//cyber",
        "//sample_component/proto:sample_component_proto",
    ],
)
```
apollo_component规则声明了该 target 是一个组件，其中：

name：该组件产出的动态库名称，与 dag 文件中读取的动态库名称一致
srcs：该组件的源文件
hdrs：该组件的头文件
deps：该组件的依赖，在这里依赖了 cyber 的接口以及组件本身 proto 下的声明 target

### 更加容易地基于 Apollo 进行功能扩展

为了让开发者可以更容易地针对自己的场景来构建自动驾驶应用 ，Apollo 除了提供各种丰富的功能组件/插件之外，还在功能扩展方面做了提升和优化

主要体现在这3种扩展场景

##### 更加简单的接口调用方式

#### 更加简单的接口调用方式

对于需要实现自定义调度逻辑的自动驾驶应用的扩展场景，Apollo 增加了统一的接口模块，并对已有的规划功能进行封装，开发者只需基于接口开发自己的调度模块即可实现自己应用场景的自动驾驶，最快能在1天内搭建好应用场景的demo

一方面保证功能使用方式的统一，开发者基于接口进行开发，避免了逻辑的耦合，而无需关注 Apollo 内部模块复杂的数据流拓扑实现；
另一方面 Apollo 对这些接口进行了分类和简化，使得结构更加清晰，使用起来更加方便
![](../images/06_工程框架/77a5e7df2ac8e92b70c9cdd464a7e509.png)

新版本Apollo针对规划模块抽象了统一的接口层CommandProcessor，将原有指令统一成命令接口的形式，更好地解耦了业务层和PNC内部模块；

| 命令名称 |  | 功能 |
| --- | --- | --- |
| LaneFollowCommand |  | 点到点沿道路行驶 |
| ValetParkingCommand |  | 泊车 |
| ActionCommand | PULL_OVER | 紧急靠边停车 |
|  | STOP | 紧急停车 |
|  | START | 继续行驶 |
|  | SWITCH_TO_MANUAL | 切换到手动模式 |
|  | SWITCH_TO_AUTO | 切换到自动模式 |
|  | VIN_REQ | vin code验证 |

比如实现一个简单的园区物流小车应用，我们可以通过LaneFollowCommand和ValetParkingCommand来实现

![](../images/06_工程框架/104140c38e17be81305ec367901d5e7d.png)

两个简单的调度场景

1、当前收发点已经取完所有货件或者一段时间内没有人前来操作，则计算出下一个收发点，调用LaneFollowCommand命令行驶至下一个收发点

2、当前处理完当前收发点货件后，如果已经处于非运营时间段，调用ValetParkingCommand命令行驶回停车区

##### 更加方便调参方式

#### 更加方便调参方式

对于 Apollo 已经涵盖了功能，但需要针对具体应用调整参数配置的扩展场景，Apollo 对参数配置管理和说明做了优化和补充，开发者可以更加快速和容易地找到需要调整的参数配置，调参效率提升1倍以上

随着 Apollo 功能的不断丰富，相应地，参数配置量也在不断地增加，为了降低开发者修改参数的难度，Apollo 对于参数配置的管理做了以下优化和调整

增加了针对应用级别的增量参数配置管理，开发者可以按照不同的使用场景（比如不同的车或者不同的区域场景）来管理配置，并且在开发调试过程中可以快速切换；
将参数按全局和局部划分（全局参数是多个算法或插件中共同使用的参数，局部变量是专属于某个算法或插件的参数），让参数配置跟随作用的范围和功能，开发者可以更方便地找到功能的相关参数配置；
补充了更多关于参数的说明文档，以便于更好地理解其功能和用法
在日常的开发和调试过程中，对于不同的场景我们可能需要对同一个模块使用不同的配置，针对这种情况我们设置了profiles目录（替换了原来的calibration/data），可以通用aem工具查看和使用

> **INFO**
> 使用profiles里的配置后实际上是在/apollo目录中的配置文件软链向profiles目录下的配置文件，所以在代码或配置中使用形如/apollo/xxx的绝对路径的逻辑会优先使用通过命令aem use <profile_name>生效后的配置

> 那么：最终查找的优先级是/apollo_workspace/modules/xx/xx.conf> /first-path/modules/xx/xx.conf> /second-path/modules/xx/xx.conf
> 具体实现可参考：
> [https://github.com/ApolloAuto/apollo/blob/9.x_alpha/cyber/common/file.cc#L402](https://github.com/ApolloAuto/apollo/blob/9.x_alpha/cyber/common/file.cc#L402)

###### 重写Init接口和ApplyRule接口

```cpp
#pragma once

#include <memory>

#include "cyber/plugin_manager/plugin_manager.h"
/* 添加了相应的头文件 */
#include "modules/common/status/status.h"
#include "modules/planning/traffic_rules/region_speed_limit/proto/region_speed_limit.pb.h"
#include "modules/planning/planning_base/traffic_rules_base/traffic_rule.h"

namespace apollo {
namespace planning {

class RegionSpeedLimit : public TrafficRule {
    /* 声明成员函数 */
 public:
    bool Init(const std::string& name,
              const std::shared_ptr<DependencyInjector>& injector) override;
    virtual ~RegionSpeedLimit() = default;
    common::Status ApplyRule(
        Frame* const frame,
        ReferenceLineInfo* const reference_line_info);
    void Reset() override {}

 private:
    RegionSpeedLimitConfig config_;
};

CYBER_PLUGIN_MANAGER_REGISTER_PLUGIN(
    apollo::planning::RegionSpeedLimit,
    apollo::planning::TrafficRule)

}  // namespace planning
}  // namespace apollo
```
```cpp
#include <memory>
#include "modules/planning/traffic_rules/region_speed_limit/region_speed_limit.h"

namespace apollo {
namespace planning {

/* 定义成员函数 */
using apollo::common::Status;
using apollo::hdmap::PathOverlap;

bool RegionSpeedLimit::Init(
    const std::string& name,
    const std::shared_ptr<DependencyInjector>& injector) {
    if (!TrafficRule::Init(name, injector)) {
        return false;
    }
    // Load the config this task.
    return TrafficRule::LoadConfig<RegionSpeedLimitConfig>(&config_);
}

Status RegionSpeedLimit::ApplyRule(
    Frame* const frame,
    ReferenceLineInfo* const reference_line_info) {
    ReferenceLine* reference_line =
        reference_line_info->mutable_reference_line();
    const std::vector<PathOverlap>& pnc_junction_overlaps
            = reference_line_info->reference_line().map_path()
                                  .pnc_junction_overlaps();
    for (const auto& pnc_junction_overlap : pnc_junction_overlaps) {
        reference_line->AddSpeedLimit(
            pnc_junction_overlap.start_s - config_.forward_buffer(),
            pnc_junction_overlap.end_s + config_.backward_buffer(),
            config_.limit_speed());
    }
    return Status::OK();
}

}  // namespace planning
}  // namespace apollo
```

##### 插件原理

插件是从运行时库（即共享对象、动态链接库）中动态加载的类，程序可以在任何时候打开包含插件类的库，而事先不必知道该库或包含类定义的头文件。通过插件机制，可以程序改造成更加容易扩展

![](../images/06_工程框架/242ce8a3237dc1f22d12a77faa9bd10f.png)

与组件类似，插件的实现利用了C++中动态加载库的机制

![](../images/06_工程框架/7206c608480a054241908a8041e864ba.png)

1、使用mainboard启动组件时，会扫描插件安装目录读取插件描述文件，然后加载对应的库文件并可构建索引和维护插件信息

2、在组件初始化时根据配置或者flag进行插件的实例化

3、在组件处理数据或运行其它任务时调用插件方法
